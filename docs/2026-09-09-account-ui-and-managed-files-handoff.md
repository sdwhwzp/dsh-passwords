## 设计取舍与被否决的方案

**工作区开关没有删除。** 用户问「工作区本来不就是每个人用自己的」——确实如此：子用户创建时自动分配专属工作区（`managed-workspace.ts`），保存权限时服务端强制把它加回白名单（`gateway.ts` 的 `managedWorkspace` 归一），权限页关不掉。该开关管的是「额外把主用户的共享工作区分给某个子用户」，留空即只有自己的目录。因此保留能力、只折叠界面；曾考虑的两个方案都被否决：整块删除会让共享工作区再也分不出去；保存时一律提交空白名单更危险——对有专属工作区的账号，服务端会把空数组改写成只剩他自己的目录，反而更严。

**会话默认关闭没有实现。** 同一原因：默认状态已经是「除自己的专属目录外什么都不给」，会话勾选只在主动共享某个工作区后才起作用。真正做到「新建会话也默认关闭」需要把服务端的 `disabled_sessions` 黑名单换成白名单（建表、迁移、网关全部会话校验反转），与当前需求不成比例。

**移动与复制用剪贴板模型**，不是让用户输入目标路径：面板本就靠点击目录导航，选中后进目标目录粘贴与现有交互一致，也不需要再做一个目录选择器。

**git 只接受 http(s)。** `ssh://` 需要宿主账号的密钥，`ext::` 会让 git 执行任意命令，`file://` 可读宿主任意路径，一律拒绝。私有仓库把访问令牌写进地址，令牌只落在该账号自己的 `.git/config` 内，回显与审计里打码。

**git 不复用编辑器/终端沙盒。** 那两条路径要 root 启动器与 sudoers pin；文件夹管理的 clone 只写该账号的托管目录，用网关进程加固后的最小环境直接跑即可，不引入新的特权入口。

## 安全约束

- 移动、复制、新建文件夹全部经原有的 `managedFilePathFor` 规范化：来源必须是已存在的普通文件或目录（符号链接拒绝），目标必须在本账号托管根内且尚不存在，不能移进自身子目录。
- git 运行参数固定 `protocol.allow=never` 加 http(s) 例外、`credential.helper=`、`core.askPass=`、`core.symlinks=false`（仓库里的符号链接写成普通文件，无法指向托管目录之外）。
- 环境只继承 PATH/LANG/TEMP 等数项，`HOME` 指向该账号托管根，`GIT_CONFIG_NOSYSTEM=1`、`GIT_CONFIG_GLOBAL=/dev/null`、`GIT_TERMINAL_PROMPT=0`：读不到宿主账号的 git 配置与凭据助手，认证失败直接报错而不是挂起。
- 需要同时具备「允许上传文件」与「允许 git 下载」两项权限；同一账号同时只允许一个 git 任务，超时 5 分钟，输出截断 8 KiB。
- 新审计事件：`managed_directory_created`、`managed_file_moved`、`managed_file_copied`、`managed_git_cloned`、`managed_git_clone_failed`、`managed_git_pulled`。

## 验证结果

- 自测 407 项通过、13 项自跳过（跳过项为既有的平台相关用例），构建通过。本轮新增 10 项。
- 端到端 git：用例内 `git init` 造仓库、`git clone --bare` + `update-server-info` 后以哑 HTTP 服务发布，经真实路由 clone 进托管目录并断言文件内容，再 `git pull` 成功。
- 拒绝路径：`ext::`、`file://`、`ssh://`、`git://`、含换行的地址、无权限账号、非仓库目录的拉取、`../escape` 目标文件夹，均按预期被拒。
- 路径安全：移动到 `../outside`、复制符号链接来源、移动托管根自身、移进自身子目录、重名覆盖，均被拒绝且未在目录外留下文件。
- 界面：以 react-test-renderer 渲染真实组件为静态页，套用 DSH 明暗两套设计令牌，在 1500px 与 760px 两种宽度核对排版；折叠态与展开态分别核对。

这些检查不替代生产浏览器验收。
